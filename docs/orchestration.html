The Conductor:
Docker Compose

Typing long CLI commands to start a database, a backend, and a frontend gets messy. Enter Infrastructure as Code.

Why Docker Compose?

Imagine running a WordPress site. You need an Nginx container, a WordPress container, and a MariaDB container. You'd have to run three massive docker run commands, manually link their networks, and mount their volumes perfectly every single time.

Docker Compose solves this. It allows you to define your entire multi-container application stack in a single, readable YAML file. One command brings the entire system up, and one command tears it down cleanly.

The docker-compose.yml File

This file acts as the master blueprint. When you run docker compose up, Compose parses this file and automatically issues the correct commands to the Docker Daemon.

version: '3.8'

services:
  mariadb:
    image: mariadb:10.5
    volumes:
      - db_data:/var/lib/mysql

  wordpress:
    image: wordpress:latest
    depends_on:
      - mariadb

volumes:
  db_data:
# Start all containers, networks, and volumes defined in your yml file in the background
$ docker compose up -d

# Stop and completely destroy all containers and networks created by Compose
$ docker compose down

The Hidden Magic: DNS & dependencies

Automatic DNS Resolution

Because WordPress and MariaDB are in the same docker-compose.yml, Docker automatically puts them on a shared Virtual Switch. Docker runs a hidden DNS server that lets the wordpress container connect to the database simply by asking for the hostname "mariadb". You never have to guess IP addresses!

Depends_On

Containers boot up fast. If WordPress boots before MariaDB is ready, WordPress will crash trying to connect to a non-existent database. The depends_on instruction tells Compose to start the mariadb container completely before it is allowed to start the wordpress container.
