Chapter 3

Kernel Magic:
The Illusion of Isolation

If containers don't have a Guest OS, how are they isolated? The answer lies in three native features of the Linux Host Kernel. Let's peel back the curtain.

User Space vs. Kernel Space

Before we look at the magic, we must define the boundaries. The Kernel Space is the highly privileged core of the OS that talks directly to physical RAM and CPUs. The User Space is the restricted area where normal applications (browsers, terminals, and Docker containers) live.

A Docker container is nothing more than a normal User Space process. But the Kernel places three strict rules on this process to trick it into thinking it's an independent computer.

1. Namespaces (The Matrix Illusion)

Namespaces put blinders on a process. They restrict what a process can see. By placing a container in its own Namespaces, the Kernel feeds it a fake reality.

PID Namespace

Inside the container, the process thinks it is PID 1. On the host computer, however, the kernel knows it's actually PID 45892.

NET Namespace

The process gets a blank network stack. It doesn't see the host's Wi-Fi card; it only sees a virtual eth0 interface.

# Execute a shell inside a running container to verify isolation
$ docker exec -it website sh

# Check network interfaces (You will only see 'lo' and isolated 'eth0')
$ ip addr

# Check processes (You will see Nginx running as PID 1)
$ top

2. cgroups (The Bouncer)

Namespaces control what a container can see, but cgroups (Control Groups) control what a container can use.

What stops a poorly written WordPress loop from eating 100% of your server's RAM and crashing the whole host? The Kernel's cgroups act as a bouncer, physically restricting the hardware resources available to the container's process.

# Run a container with strict cgroup limits (Max 512MB RAM, max 1.5 CPU cores)
$ docker run -d --memory="512m" --cpus="1.5" nginx

3. chroot (The Fake Filesystem)

When you run ls /bin in a container, where do those files come from? They aren't your host machine's files!

This is done using chroot (Change Root). When Docker downloads an Image (like Alpine), it is essentially downloading a compressed folder full of a tiny Linux filesystem.

When the container starts, the Kernel uses chroot to physically lock the process inside that downloaded folder. The process cannot look "up" or "out" to the host's actual hard drive. It is jailed.
