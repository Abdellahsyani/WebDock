Security & Anti-Patterns

Getting a container to run is easy. Securing it and following industry standards separates the beginners from the professionals.

1. Secure Passwords & .env Files

Never hardcode passwords in your Dockerfile or docker-compose.yml. If you push that file to GitHub, your entire database is compromised.

The .env File

Store sensitive variables in a local .env file. Docker Compose will automatically read this file and inject the variables (e.g., ${MYSQL_PASSWORD}) into the containers at runtime. Always add .env to your .gitignore.

Docker Secrets

For maximum security, use Docker Secrets (or MYSQL_PASSWORD_FILE). Instead of an environment variable, Docker reads a protected file on your host and mounts it directly into the container's memory, completely hiding it from docker inspect commands.

2. Avoid the "Anti-Patterns"

Evaluators will instantly fail your infrastructure if you commit these common Docker sins:

  • ❌ The "Fat" Container Do not install Nginx, PHP, and MySQL all inside a single Dockerfile. Containers are not Virtual Machines! Rule: One primary process per container.
  • ❌ Running as Root By default, Docker processes run as the root user. If a hacker breaches your Nginx container, they have root access. Rule: Create and switch to a non-root user (e.g., USER www-data) at the end of your Dockerfile.
  • ❌ Storing Data inside the Container Never let a database save its tables inside the container's ephemeral Read-Write layer. Rule: Always mount a Volume for persistent data directories.
